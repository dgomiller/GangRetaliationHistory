## 2. How it works

- **Message capture:** observes `GRDetection:Notify(text)` from Lua; every on-screen message of the main mod goes through it, including the direct calls in `Integrations.reds`. (#16) A log line is `ts | campaign C | day D | <KEY> | <args> | <text as shown>`; KEY = the main mod's message key (`GR-MsgPromoted`, ...), args are tokens joined by `^` with `~` inside (`N~name~title~gangLabel`, `R~R3|R3F|R2|R1`, `G~gangLabel`, `P~text`, `T~k:<traitKey>|r:<raw>`). Unmatched lines stay `NEWS | text`. The screen re-renders each event in the active language from key + args (`Tagger.render`). Old v1 lines are converted on first load (original kept once as `data/history.log.v1.bak`; in-game `os.rename` of the log fails, so `init.lua` falls back to rewriting in place). [verified] (#35, #38)
- **Why language-neutral:** CET confines `io.*`, `os.rename/remove`, `require`, `dofile` to the mod's own folder (a CET mod cannot read another mod's files); redscript has no file access; nemesis TITLES are not localization keys (they live in the main mod's Lua data as `titleEn`/`titleEs`), so titles cannot be translated from outside and are shown as recorded. Codeware's `ModLocalizationProvider.GetPackage(language)` is public if cross-language strings are ever needed. [verified] (#35)
- **Portability:** never assign to a `for` loop variable (newer Lua rejects it; found by the lupa tests). (#35)
- **Localization:** a Codeware `ModLocalizationProvider` (module `GangRetaliationHistory.Localization`), English and Spanish packages (es-es and es-mx share one), keys prefixed `GRChron-`. Screen text goes through `GRChronText(gi, key, englishFallback)`. Reuses the main mod's keys where they exist (`GR-MenuDay`, `GR-MenuAlive`, `GR-MenuFallenShort`, `GR-MenuEmpty`, `GR-Rank*`). Message gang labels always come from `Names.gangLabel` (English in both languages). Spanish vocabulary follows the main mod: Némesis, Jefe/Teniente/Soldado, Caídos/Vivos, DÍA %d, Rasgos, Emboscadas, redada, Cara nueva, Lucha interna. [compile-verified] (#33)
- **Event kinds tagged** (`modules/tagger.lua`): RAID (Barghest raids and escapes), STRONGHOLD (gold), WEAPON (cyan, tagged with boss and gang by scanning text, `Tagger.tagEvent`), INTEL (`GR-IntelGained` / `GR-IntelLocated`, `{gang}`/`{pct}` normalized to `%s`). Not Notify messages and ignored: `GR-MsgGangFull` (debug log), `GR-MsgTWRThreat/Refuse` (phone texts). If the author changes message templates, update `Tagger.KEYS`; unmatched messages fall back to NEWS (grey). (#42, #43, #51)

## 3. Screen and UI

- A screen's ink resource is trivial: an `inkWidgetLibraryResource` with one empty 3840x2160 `inkCanvasWidget` "Root" whose gameController is a built-in `DynamicWidgetController` with `"$className": "<Module>.<ScriptClass>"`. Built from JSON with WolvenKit.CLI (convert deserialize, then pack); see `build/build_archive.py`. [verified] (#25)
- Look matching the Nemeses screen: cards are two `inkImage` layers from `base\gameplay\gui\common\shapestlas_shapes_sync.inkatlas`, parts `cell_bg` (fill) and `cell_fg` (outline), `SetNineSliceScale(true)`. Tabs: 236x60 canvas per gang, label anchored TopCenter, 4 px bar at the bottom (8 px and cyan when active). (#29)
- Structure: tab 0 = FULL HISTORY (left: "All History" card then one card per gang; right: every event or the chosen gang's, rows show the gang under the tag); tabs 1..n = one per gang (left: "All Gang History", then members alive-by-rank then dead). `m_member` holds a member name on gang tabs and a gang key on Full History; "" = the All card. (#30)
- Scrolling: inkCanvas host (interactive) > inkScrollArea (`SetUseInternalMask(true)`, `SetConstrainContentPosition(true)`) > inkVerticalPanel; an `inkScrollController` attached to the host handles the wheel. No horizontal scrollbar hook exists: draw the indicator by hand from the scroll area's `OnScrollChanged`. The first version's scroll code resembled Ping's (theCyanideX, Nexus 34933, no reuse without permission), so it was REWRITTEN with hand-drawn indicators; reworked again into native-style draggable slider bars after an in-game test. (#28, #37)
- Header switcher (1.2.0): TAB hint + GANGS | TERRITORY | ARSENAL | HISTORY (HISTORY highlighted). Clicking the first three opens `gangretaliation_nemesis_menu` via `GRMenuData.RequestView(gi, n"gangs"/"territory"/"arsenal")` then `OnOpenMenu` (one-shot). TAB (`sort_list`) on History opens GANGS via `OnGRChronOpenGangs`; title at y=184 to match his. The separate hub button under Character was removed: History is reached from his switcher (his scenario handler is `OnGangRetaliationOpenHistory`, guarded by `ModuleExists`; ours is menu name `gangretaliationhistory_history_menu`). [verified in game] (#44, #47-#50)
- "Current Day: N" (ES "Día actual: N", key `GRChron-Today`), 50 pt cyan top right, value `floor(GRSpawner:GetGameDay())`, computed once on open. (#45, #46)
- Opening the screen within a second or two of loading a save can show "No Nemeses yet" (the main mod pushes its roster a few seconds after load); it fills in when reopened. Accepted; if a user reports it, add a 1-second re-check while the roster is empty. Loading an earlier save does not rewind history (only day labels can go backwards). (#39, #41)

## 4. Gang Retaliation dependencies and update checklist

The History mod depends ONLY on these public pieces; confirm each after a Gang Retaliation update (#34):
- `GRDetection:Notify(text: String)` (Detection.reds), `GRSystem:GetCampaignId()`, `GRSpawner:GetGameDay()` (Core.reds / Spawner.reds)
- `GRMenuData.Get(gi)` / `GetEntries()` / `Text(key)`; `GRMenuEntry` fields `gangKey, gang, rank, dead, name, title, renown, cause`; `GRBorder`
- message keys `GR-Msg*`, `GR-MenuDay`, `GR-MenuAlive`, `GR-MenuFallenShort`, `GR-MenuEmpty`, `GR-Rank*`; `GRMenuData.RequestView`

Steps: (1) back up the three places the mod lives into `Other/`; (2) diff the new vendor zip against the previous one by hashing files; (3) check the list above; (4) run the offline compile check with the NEW main-mod scripts copied into the scratch tree (the checker reads the INSTALLED ones) and `build/test_chronicle.py`; (5) update `Tagger.KEYS` if templates changed; (6) Expanded Names: compare `names.lua` SHA-256 prefix to `8E5824FFE82B`, merge instead of overwriting if it differs (it was unchanged through 1.4.0 and 1.4.5); (7) a redscript compile error disables ALL script mods for that launch: if the "REDScript compilation failed" popup appears after an update, delete `r6/scripts/GangRetaliationHistory` first.

## 7. Release routine, pending items and small facts (added 2026-11-17)

- **Releasing a History version:** bump `VERSION` in `build/build_release.py`, `init.lua` (`local VERSION`) and the hook-print assertion in `build/test_chronicle.py`; add the `CHANGELOG.md` section; update `README.md` / `NEXUS_DESCRIPTION.txt` if the text changes (requirements, how to open the screen); run `python build/build_release.py` (pre-flight compile + Lua tests + version check, then zip into `Distribution/GangRetaliationHistory/<version>/`). Install the changed files into the game only when it is not running, then `cmp` them against the zip. The user uploads to Nexus himself: new main file, changelog line, keep the AI-disclosure box, archive the previous version when the new one needs a newer Gang Retaliation. Nothing is uploaded without his go-ahead.
- **Requirement of 1.2.0:** Gang Retaliation 1.4.5 or newer (calls `GRMenuData.RequestView`; fails to compile on older versions, and a compile error disables all script mods for that launch). Users on older versions use History 1.1.1. The requirements line on the Nexus page says so.
- **Expanded Names is now merged into Gang Retaliation's own `names.lua`.** [2026-11-17, Nova approved] No longer a separate Vortex patch layered on top: the main mod's own `modules/names.lua` on the `RedFalcon` branch now ships the expanded ~40-50-per-gang lists directly (same function logic as before). See `../GangRetaliation/NOTES.md` section 2. The standalone `GangRetaliationExpandedNames` project/zip still exists untouched for people on an older Gang Retaliation without this merge, but there's no longer a "never overwrite names.lua" caution for our own copy of the main mod.
- **Tagger.KEYS updated for Gang Retaliation's 2026-11-17 message additions** (non-lethal knockout promotion, dismembered-flavor variants, knocked-out-then-returned): added `GR-MsgKnockedOut`, `GR-MsgKnockedOutDismembered`, `GR-MsgFledDismembered`, `GR-MsgEscapedDismembered`, `GR-MsgAgainEscapedDismembered` (all tagged `"ESCAPED"`, same category as the existing fled/escaped entries) and `GR-MsgReturnedKnockedOut` (tagged `"RETURNED"`). No new category/color/UI wiring needed since both tags already exist in `History.reds`. Checked with a one-off script (parse + classify + render round-trip for all six, not in `build/test_chronicle.py`'s fixture since it predates these messages) — all six pass. Deployed to the game folder; not yet confirmed in game.
- **Switcher geometry** (to match his screen): his panel `view_switch` sits at margin 120,258 with a TAB key tag (bordered, cyan) then GANGS | TERRITORY | ARSENAL (32 pt Bold, grey, separators " | "); active entry cyan; his title is 64 pt Medium red at margin 120,184. Our tab keys are `option_switch_prev` / `option_switch_next` (A / D) for gang tabs and `sort_list` (TAB) to return to GANGS. The HISTORY entry on his side is built in his `Menu.reds` (`OpenHistory`, `GRHasHistory()`), his `ToggleView` goes ARSENAL -> HISTORY when History is installed.
- **Opening a menu from a menu** (works in game): keep the dispatcher from an `OnSetMenuEventDispatcher` override (call `super.` first), fire `SpawnEvent(n"<EventName>")`, and handle that event in an `@addMethod(MenuScenario_HubMenu)` callback that calls `this.OnOpenMenu(n"<menu name>", null)`. Use a unique event / handler name per mod to avoid clashes. His mod also offers `GRMenuData.OpenView(from, view)` as a one-call alternative; we do not use it.
- **Intel messages:** `GR-IntelGained` fires on every gain, so a busy session adds many "<gang> intel: N %" rows. If that proves noisy, options: collapse consecutive gains for the same gang, or add a filter by tag (not built).
